# Security

## Reporting a vulnerability

Use GitHub's [private vulnerability
reporting](https://github.com/shurikai/role-model/security/advisories/new) for
anything exploitable. Please don't open a public issue for it first.

This is a personal project maintained by one person in their own time. Expect a
reply within a week, and expect a fix to take longer than that.

## What this software is

**Single-user, self-hosted, and it trusts its operator.** One person, one
instance, their own database, their own Anthropic key. It is not multi-tenant:
every tenant-scoped table carries a `user_id` and every query filters on it,
but that is groundwork for a possible future rather than an isolation guarantee
anyone should rely on today. Do not run one instance for several people who
should not see each other's data.

## Deploying it without hurting yourself

The defaults assume you are behind a firewall or on your own machine. If you
put an instance somewhere reachable, four things matter more than the rest.

**`JWT_SECRET` must be long and random.** The server refuses to start without
at least 32 characters, because an empty secret signs every token with a
zero-length key and there is no symptom at all — signup succeeds, login
succeeds, and every token is forgeable by anyone who can guess a user's UUID.
`openssl rand -base64 32`.

**Signup is closed by default outside development**, and should stay closed
once you have your account. An open signup on a reachable instance lets anyone
create an account and spend your API key.

**The renderer must not be reachable.** `docx-renderer` has no authentication,
no request size limit and no CORS configuration, because it was built to sit
behind the API on a private network. The compose file does not publish its
port. Do not add one.

**The database port is published for convenience.** `docker-compose.yml` maps
5433 so `psql` and the integration tests can reach it. That is a development
convenience; drop the mapping on anything exposed.

## What is in place

- bcrypt at default cost; identical errors for unknown-email and bad-password,
  so login does not enumerate users
- Every authenticated route behind one middleware, and every user-scoped query
  filtered on `user_id`; the few join-table writes that cannot be are guarded
  by explicit double-ownership checks in the handler
- Parameterised SQL throughout, generated by sqlc — no string-concatenated
  queries anywhere
- Rate limiting on the auth routes and on the five endpoints that spend your
  API key; a 2 MB request body cap
- Timeouts on the server, the renderer client and the model client
- CORS fails closed when unset outside development; the containerised path
  serves the API from the same origin and needs none

## What is not

Named plainly, because a list of controls without its complement is marketing.

- **No refresh or revocation.** Tokens last 24 hours and live in
  `localStorage`. A stolen token is valid for a day and there is no way to kill
  it. Logging out clears the client only.
- **No password reset in the app.** `make reset-password` writes a new hash
  directly and needs shell access.
- **No audit log, no usage accounting.** Nothing records who spent what against
  your API key.
- **No secrets management.** Configuration is environment variables and a
  `.env` file.
- **`X-Forwarded-For` is deliberately not trusted** by the rate limiter, so
  behind a reverse proxy every client looks like the proxy. Rate limit at the
  proxy instead.

## Your data and your key

Both stay on your machine. Career history is in your Postgres; the Anthropic
key is yours, in your environment, billed to you. This project ships no
credentials and phones nothing home. The only outbound calls are to the
Anthropic API, from your server, with your key.
